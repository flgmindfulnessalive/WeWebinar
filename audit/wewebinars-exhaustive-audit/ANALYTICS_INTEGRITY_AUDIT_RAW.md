## 2. CONFIRMED FINDINGS

### F-01 — CTA click conversion % can exceed 100% (raw click count is not deduped per registrant) — **P1, High confidence**

**Evidence:**
- `record_viewer_event` performs a bare `INSERT` with no idempotency key for `cta_click`: `/home/user/WeWebinar/supabase/migrations/20260822000003_functions_and_triggers.sql:445-447`.
- `get_webinar_cta_stats` computes `clicks` as `count(*)` over raw `cta_click` events, **not** `count(distinct registrant_id)`: `/home/user/WeWebinar/supabase/migrations/20260903000004_separate_cta_poll_analytics.sql:43-49` (`clicks as (select ... count(*) as clicks ... group by cta_id)`).
- `conversion_pct = 100.0 * clicks / attendee_count` with no `LEAST(..., 100)` cap: same file, lines 51-60.
- The client fires `recordCtaClick(cta.id)` from **two simultaneously-visible surfaces for the same CTA**: the on-video overlay (`onLinkClick={() => recordCtaClick(cta.id)}`, `/home/user/WeWebinar/src/app/[locale]/w/[accountSlug]/[webinarSlug]/live/[token]/live-room-client.tsx:507`) and the "Avisos" notifications tab, which independently lists every CTA that has appeared so far (`notificationCtas`, line 362) with its own click handler (`onLinkClick={recordCtaClick}` inside `NotificationCard`, line 586). Both remain clickable for the same `cta_id` at the same time (`activeCtas` and `notificationCtas` are computed independently, lines 351-362).

**Condition:** A single attendee clicks a link-type CTA once in the overlay, then switches to the "Avisos" tab and clicks the same CTA card there — a completely normal, non-malicious interaction pattern (e.g. re-checking the notification later). Two `cta_click` events are recorded for one registrant. Same result from a double-click, a slow network causing a client retry (there is no retry-guard in `recordViewerEvent`, `/home/user/WeWebinar/src/app/[locale]/w/[accountSlug]/[webinarSlug]/live/[token]/live-room-client.tsx:184-201`, but even a single successful click from two UI surfaces already reproduces it), or the reader clicking, going "back", and clicking again.

**Expected vs actual:** Expected: conversion_pct ∈ [0, 100], one click = one converted registrant. Actual: `clicks` can exceed `attendee_count` for that CTA, producing e.g. 150–200% conversion shown in the "Clics por CTA" bar chart (`/home/user/WeWebinar/src/app/dashboard/webinars/[id]/analytics/page.tsx:248-254`) and in the CSV-adjacent PDF report (`ctaClicksValueLabel`, `/home/user/WeWebinar/src/app/api/webinars/[id]/report/route.tsx:255-261`).

**Reproduction:** With one registrant token: call `record_viewer_event(token, 'cta_click', ts, {"cta_id": "<id>"})` twice (or click the overlay CTA, then click the same CTA again from the Avisos tab). Query `get_webinar_cta_stats(webinar_id)` — `clicks=2`, `attendee_count=1` → `conversion_pct = 200.0`.

**Remediation:** Dedupe `clicks` the same way `poll_response` is already deduped: either `count(distinct registrant_id)` for the conversion-rate numerator (keep raw `count(*)` separately as "total clicks" if that's wanted), and cap `conversion_pct` at 100 defensively. Separately, decide whether the Avisos-tab CTA card and the on-video overlay should share one "already clicked" client-side state (similar to how polls already track `pollAnswers`) so the same registrant isn't prompted to click twice at all.

### F-02 — "Attendee" has two different denominators across analytics RPCs — **P2, High confidence**

**Evidence:**
- `get_webinar_summary` / `get_webinar_retention_curve` / `get_webinar_schedule_performance` / `get_webinar_watch_positions` / `get_webinar_lead_scores` all define "attendee"/"watched" as **registrants with ≥1 `viewer_events` row where `video_timestamp_seconds IS NOT NULL`** — e.g. `/home/user/WeWebinar/supabase/migrations/20260830000010_registration_page_views.sql:80-91` (`watch` CTE, filters `video_timestamp_seconds is not null`).
- `get_webinar_cta_stats`'s own internal "attendees" CTE instead counts **any** `viewer_events` row regardless of `video_timestamp_seconds`, i.e. it also counts registrants whose only row is a `join` event with `video_timestamp_seconds = null`: `/home/user/WeWebinar/supabase/migrations/20260903000004_separate_cta_poll_analytics.sql:37-42` (`attendees as (select count(distinct ve.registrant_id) ... from viewer_events ve where ve.webinar_id = ... )` — no `video_timestamp_seconds is not null` predicate, no `event_type` filter).
- Since `join` (`live-room-client.tsx:250`) is fired with **no** `videoTimestampSeconds` (`recordViewerEvent("join")`, no `opts`), a registrant who loads the room and leaves before the first 15s heartbeat generates only a null-timestamp `join` row.

**Condition:** Any registrant who opens the live room but disconnects (closes tab, network drop, crash) inside the first `HEARTBEAT_INTERVAL_MS` (15s) window, before any heartbeat/leave/cta/reaction/poll event lands.

**Expected vs actual:** Expected: the word "attendee" means the same population everywhere on the dashboard/exports. Actual: that registrant is **excluded** from `attendee_count` in the main KPI tile, funnel, retention curve, watch-positions, and lead scoring, but **included** in the `attendee_count` used as the denominator for CTA `conversion_pct` in the very same page (`get_webinar_cta_stats`, rendered directly under the funnel that used the other definition, `/home/user/WeWebinar/src/app/dashboard/webinars/[id]/analytics/page.tsx:341-361` vs `:248-254`). This silently produces a lower/different CTA conversion % than a host would compute by hand from the "Actual attendees" stat tile.

**Remediation:** Standardize on one "attendee" definition (recommend: has ≥1 event with non-null `video_timestamp_seconds`) and reuse it in `get_webinar_cta_stats`'s `attendees` CTE, matching the other RPCs.

### F-03 — CSV export and PDF report always report all-time totals, silently ignoring the dashboard's active date-range filter — **P2, High confidence**

**Evidence:**
- Dashboard page passes the selected range to (almost) every RPC: `/home/user/WeWebinar/src/app/dashboard/webinars/[id]/analytics/page.tsx:99-140` (`p_start_date`/`p_end_date` derived from `DateRangeSelect`/`analyticsRangeToDates`).
- CSV export route calls `get_webinar_watch_positions` / `get_webinar_lead_scores` with **only** `p_webinar_id` (`/home/user/WeWebinar/src/app/api/webinars/[id]/export/route.ts:61-64`) and reads `registrants` with a plain `.eq("webinar_id", webinarId)` (no date filter at all, lines 55-60) — no `range` query param is even read from the request.
- PDF report route calls **every** analytics RPC with only `p_webinar_id`, no start/end date, for all 12 RPCs it fans out to: `/home/user/WeWebinar/src/app/api/webinars/[id]/report/route.tsx:75-89`. The report even hardcodes its own "range" label to "all": `dataRangeLabel: tReport("dataRangeAll")` (line 291).
- The dashboard's download buttons sit directly beside the `DateRangeSelect` control with no indication they ignore it: `/home/user/WeWebinar/src/app/dashboard/webinars/[id]/analytics/page.tsx:313-329`.

**Condition:** A host filters the dashboard to "This month" (or any range other than "all"), sees e.g. 42 registrants / 30% CTA conversion for that period on screen, then clicks "Download Report" (PDF) or "Export CSV" expecting a document matching what's on screen.

**Expected vs actual:** Expected: exported numbers match the currently-displayed, currently-filtered numbers (or the UI clearly states the export is always all-time). Actual: both exports silently return **all-time** totals — different registrant lists, different lead scores, different CTA/poll numbers than what's on screen — with no warning in the UI copy (`downloadReport`/`exportCsv` button labels carry no "all time" qualifier, only the PDF's own internal caption does, which the host never sees before downloading).

**Remediation:** Either (a) thread `range`/`p_start_date`/`p_end_date` through both export routes the same way the dashboard page does, or (b) if "always all-time" is the intended, permanent product decision, say so on the buttons themselves (e.g. "Export CSV (all time)") so the numbers can't be mistaken for the filtered view.

### F-04 — "Watch time" / retention is wall-clock time since page mount, not verified video playback, and the server accepts any reported position with no plausibility check — **P1, High confidence**

**Evidence:**
- `getElapsedSeconds()` is defined purely as `elapsedAnchorRef.current + (Date.now() - mountedAt) / 1000` — a wall-clock timer, not a read of the actual player position: `/home/user/WeWebinar/src/app/[locale]/w/[accountSlug]/[webinarSlug]/live/[token]/live-room-client.tsx:168-176`. The authors' own comment confirms this is deliberate: "the fake viewer count, CTA timing, and chat all key off `getElapsedSeconds()`... never off `player.currentTime`" (lines 57-64).
- Every `video_timestamp_seconds` value sent to `record_viewer_event` — heartbeat (line 267), leave (line 252), reaction (line 366), cta_click (line 373), poll_response (line 382) — is `Math.round(getElapsedSeconds())`, i.e. the wall-clock value, not `player.currentTime`.
- `handleTimeUpdate` (lines 299-317) actively **seeks the real player forward** to match the wall-clock anchor whenever the two drift by more than `DRIFT_TOLERANCE_SECONDS` (6s), rather than the reverse — so on a real stall/buffer, the *reported* elapsed time keeps climbing at 1x wall-clock speed while actual playback is paused/catching up, and the player is later force-seeked past whatever wasn't buffered.
- Server-side, `record_viewer_event` (`/home/user/WeWebinar/supabase/migrations/20260822000003_functions_and_triggers.sql:425-451`) does **no** validation on `p_video_timestamp_seconds`: no monotonicity check, no bound against `webinars.duration_seconds`, no rate limit, no check that it increases at a rate consistent with real time between heartbeats. It is granted to `anon` (line 453) and reachable directly with only a registrant's `access_token`, which is included in every confirmation/reminder email link and the room URL itself — i.e. it is not a secret in any strong sense.

**Condition / reproduction:** With a valid `access_token` (readable from the room's own URL/query string, or a reminder email), a script can call `record_viewer_event(token, 'heartbeat', 99999, {})` once, with **zero** page load, zero video playback, and be recorded as having watched to `duration_seconds` (or beyond). `get_webinar_retention_curve` and `get_webinar_lead_scores` (`watch_pct`, capped at 1.0 via `least(1.0, ...)`, `/home/user/WeWebinar/supabase/migrations/20260901000001_lead_scoring.sql:101,108`) would both report 100% retention/watch for that registrant.

**Expected vs actual:** Expected: "watch time"/retention reflects genuine video playback exposure, resistant to a background tab, a stalled/buffering player, or a direct scripted call. Actual: it is a self-reported wall-clock value with no corroboration against actual player state and no server-side sanity bound.

**Remediation:** At minimum, clamp `p_video_timestamp_seconds` server-side to `[0, duration_seconds]` and to a plausible delta since the registrant's last event (`occurred_at` diff), reject/flag anomalous jumps, and add a per-registrant rate limit on `record_viewer_event` mirroring the one already built for `post_registrant_message` (`/home/user/WeWebinar/supabase/migrations/20260827000007_rate_limit_chat_messages.sql`). Consider tying "watched" more closely to actual player state (e.g. periodically report `player.currentTime`, not only the wall-clock anchor) if genuine engagement (not just tab-open time) needs to be measurable.

### F-05 — `record_viewer_event` has no rate limit, unlike `post_registrant_message` — unbounded write amplification and self-serve lead-score inflation — **P2, High confidence**

**Evidence:**
- `post_registrant_message` was explicitly hardened with a 10-messages/minute cap after an incident where unbounded chat-message writes also drove AI-reply API spend (comment explains the incident): `/home/user/WeWebinar/supabase/migrations/20260827000007_rate_limit_chat_messages.sql:1-7,35-41`.
- `record_viewer_event`, which is exposed to `anon` the same way and used far more frequently (every 15s per active viewer, plus every click/reaction/poll vote), has **no equivalent limit**: `/home/user/WeWebinar/supabase/migrations/20260822000003_functions_and_triggers.sql:425-453`.
- `get_webinar_lead_scores` derives `clicked_cta`/`answered_poll`/`reacted`/`attended`/`watch_pct` straight from `viewer_events` with no server-side corroboration beyond "row exists": `/home/user/WeWebinar/supabase/migrations/20260901000001_lead_scoring.sql:70-113`.

**Condition:** Any registrant (or a script holding their `access_token`) can call `record_viewer_event` an unbounded number of times per second with any `event_type`, inflating: (a) row volume in `viewer_events` with no cost control, and (b) their own `lead_score` to the maximum 100 ("caliente" tier) by firing one `cta_click`, one `poll_response`, one `reaction`, and a high `heartbeat` timestamp — none of which require actually attending.

**Expected vs actual:** Expected: lead score reflects real engagement signals a sales team can trust; write endpoints have basic abuse protection consistent with the rest of the app. Actual: every input to lead scoring is self-reported and unrate-limited; a registrant (accidentally via a buggy browser extension, or deliberately) can present as a "hot lead" with zero real engagement.

**Remediation:** Add the same per-registrant/per-minute rate limit used for chat messages to `record_viewer_event`, and consider constraining "lead-worthy" signals to server-corroborated events (e.g. heartbeat cadence consistent with real elapsed time) before feeding them into the score shown to paying customers.

### F-06 — CTA click totals shown to the host are not deduped for the same underlying reason poll votes were explicitly fixed for — **P2 (design-pattern inconsistency), High confidence**

**Evidence:**
- `20260828000005_dedupe_poll_votes.sql:1-6` explicitly documents the exact same bug class for polls ("nothing stopped ... a viewer clicking several options ... each click landed as its own row") and fixed it with the `DISTINCT ON (registrant_id, cta_id) ORDER BY occurred_at DESC` pattern, reused consistently in `get_webinar_poll_results`, `get_webinar_poll_voters`, and the token-scoped `get_cta_poll_results` (`/home/user/WeWebinar/supabase/migrations/20260828000006_cta_poll_results_rpc.sql:35-47`).
- The equivalent fix was never applied to `cta_click` (`get_webinar_cta_stats`, `get_webinar_cta_clickers`) — see F-01. `get_webinar_cta_clickers.click_count` (`/home/user/WeWebinar/supabase/migrations/20260829000002_analytics_date_range_filter.sql:280-302`) explicitly surfaces the raw, undeduped per-registrant click count, which is fine as a raw count *if labeled as such*, but it currently feeds directly into `get_webinar_cta_stats.conversion_pct`'s numerator without being deduped for that specific purpose (F-01).

**Remediation:** same as F-01; noting separately because it shows the team has the right pattern already in the codebase (polls) and just needs to apply it consistently to CTAs.

### F-07 — `get_webinar_summary`'s single date-range parameter pair is applied against two different timestamp columns for different rows in the same result — **P3, Medium confidence**

**Evidence:** `/home/user/WeWebinar/supabase/migrations/20260830000010_registration_page_views.sql:63-98`. `registrant_count`/`attendee_count`/`avg_watch_seconds` are filtered by `registrants.created_at` (via `reg_ids`, lines 63-69), while `visit_count` is filtered by `page_views.occurred_at` (lines 73-79). Both use the *same* `p_start_date`/`p_end_date` pair from one date-range selector in the UI (`/home/user/WeWebinar/src/app/dashboard/webinars/[id]/analytics/date-range.ts`, `page.tsx:99-103`).

**Condition:** A registrant visits the registration page on day 1 (a `page_views` row with `occurred_at` = day 1) but only completes registration on day 3 (a `registrants` row with `created_at` = day 3). Filtering to "day 1 only" counts their visit but not their registration; filtering to "day 3 only" counts the registration but not the originating visit.

**Expected vs actual:** Expected (implied by the UI showing "Visits → Registrants" as one funnel with one date range): the visit and the registration it produced are treated as the same cohort. Actual: `visitToRegistrantPct` (`registrantCount/visitCount*100`, `/home/user/WeWebinar/src/app/dashboard/webinars/[id]/analytics/page.tsx:171-172`) mixes two different day-boundaries of the same underlying journey, most visible for evergreen/just-in-time webinars where registration can lag the visit by days. Low severity because for the common case (same-session registration) the two timestamps are seconds apart and land in the same bucket for any range wider than a day.

**Remediation:** Document this as an accepted approximation, or (cleaner) start tracking `page_views` per-visitor (a token/cookie) and count only visits that belong to the same funnel cohort as the registrants in range.

### F-08 — `viewer_events` (and `page_views`, `registrant_messages`) have no retention/archival policy — unbounded growth per webinar per viewer forever — **P3, Medium confidence (needs load data to size impact)**

**Evidence:** No `DELETE`/archival cron or scheduled job targeting `viewer_events`, `registrant_messages`, or `page_views` exists anywhere in `/home/user/WeWebinar/supabase/migrations/*.sql` (grep across all 116 migrations found none). Combined with F-05 (no rate limit on the highest-volume write path — heartbeats every 15s per active viewer, indefinitely for any registrant whose tab stays open per the `isEnded` guard note at `/home/user/WeWebinar/src/app/[locale]/w/[accountSlug]/[webinarSlug]/live/[token]/live-room-client.tsx:259-270`), this table has no upper bound on row count for a long-running or high-traffic evergreen webinar.

**Indexing gap that compounds this:** the every-RPC date-range filter (`reg_ids` CTE) filters `registrants` by `(webinar_id, created_at)`, but the only indexes on `registrants` are `(webinar_id)` and `(webinar_id, email)` — no `created_at` column in any index (`/home/user/WeWebinar/supabase/migrations/20260822000002_tables.sql:175-176`). Likewise `viewer_events`' only indexes are `(registrant_id)` and `(webinar_id, event_type)` (`/home/user/WeWebinar/supabase/migrations/20260822000002_tables.sql:233-234`) — none cover `video_timestamp_seconds IS NOT NULL` (used by `watch` CTEs in `get_webinar_summary`/`get_webinar_retention_curve`/`get_webinar_lead_scores`/`get_webinar_schedule_performance`) or `occurred_at` (used for date-adjacent ordering in poll/CTA "latest response" queries and concurrent-viewer interval joins).

**Remediation:** add `registrants (webinar_id, created_at)`, and consider `viewer_events (webinar_id, video_timestamp_seconds) where video_timestamp_seconds is not null` as a partial index for the "watch" CTE pattern used by 4+ RPCs; add a retention/archival job (or partition by month) for `viewer_events` before it becomes a scale problem, and pair it with the rate limit from F-05 to bound growth rate as well as total size.

### F-09 — Cross-tenant isolation for all `security invoker` analytics RPCs is correctly enforced by RLS — **CONFIRMED SAFE, not a finding, documented for completeness**

**Evidence traced:** every analytics RPC audited (`get_webinar_summary`, `get_webinar_retention_curve`, `get_webinar_cta_stats`, `get_webinar_poll_results`/`_voters`, `get_webinar_cta_clickers`, `get_webinar_watch_positions`, `get_webinar_registrant_messages`, `get_webinar_schedule_performance`, `get_webinar_lead_scores`, `get_webinar_country_breakdown`, `get_webinar_reactions`, `get_account_summary`, `get_account_recent_registrants`) is declared `security invoker` (no elevated privilege) and takes a raw `p_webinar_id`/`p_account_id` with **no explicit ownership check in the function body**. This means, on its face, an authenticated user from Account A could call e.g. `get_webinar_summary(p_webinar_id => '<account-B-webinar>')` directly via the Supabase client (bypassing the dashboard page's own `webinar.account_id !== current.account.id → notFound()` guard at `/home/user/WeWebinar/src/app/dashboard/webinars/[id]/analytics/page.tsx:97`).

However, tracing the underlying table RLS policies (`/home/user/WeWebinar/supabase/migrations/20260822000004_rls_policies.sql`) confirms this fails closed, not open:
- `registrants_select_members` (line 156-158) and `viewer_events_select` (line 190-192) both gate `SELECT` on `is_account_member(webinar's account_id)` — evaluated against the **caller's own** `auth.uid()`, independent of the `p_webinar_id`/`p_account_id` argument passed to the RPC.
- Because `security invoker` functions execute with the caller's own row-visibility rules, a cross-tenant call's inner `registrants`/`viewer_events` CTEs resolve to **zero rows** for a non-member caller, regardless of the (attacker-controlled) function parameter. Aggregates built on `count()`/`avg()` over an empty set correctly resolve to `0`/`NULL`, not another account's real numbers.
- The one partially-public table in the join graph, `ctas` (`ctas_select`, line 142-144, visible to `anon` for any `status='published'` webinar via `can_view_webinar`), only exposes non-sensitive marketing config (CTA type/timing/text/url) that is already visible on the live public page itself — not attendee PII or real engagement counts, which come from the properly-gated `viewer_events`/`registrants` tables.

**Conclusion:** no cross-tenant analytics leak found in the RPC surface audited. This relies entirely on RLS being enabled and correct on `registrants`/`viewer_events`/`registrant_messages` (confirmed: `alter table ... enable row level security` for all three, lines 10-14) — any future migration that adds a new analytics RPC referencing these tables, or that weakens their `SELECT` policy, should be re-checked against this same reasoning. `get_account_summary`/`get_account_recent_registrants` (`/home/user/WeWebinar/supabase/migrations/20260823000008_account_dashboard_rpcs.sql`) rely on the identical mechanism and were traced the same way.

The newer SECURITY DEFINER admin-facing RPCs checked (`get_platform_scorecard`, `get_platform_metrics_brief`, `get_growth_attribution_list`) all contain **explicit** `is_platform_admin()`/`is_growth_operator()` guards inside the function body (e.g. `/home/user/WeWebinar/supabase/migrations/20260828000007_platform_scorecard_rpc.sql:22`, `/home/user/WeWebinar/supabase/migrations/20260902000001_platform_daily_brief.sql:140`, `/home/user/WeWebinar/supabase/migrations/20260910000008_growth_attribution_list_rpc.sql:34`) — correct pattern for `security definer` functions that need to bypass RLS.

### F-10 — Concurrent-viewer presence counting can over-count during a disconnect/reconnect gap, and is currently disabled in the UI — **P3, Low confidence (no live data to size the error)**

**Evidence:** `/home/user/WeWebinar/supabase/migrations/20260828000003_schedule_performance_and_concurrent_viewers.sql:116-135`. `presence` uses `min(occurred_at) filter (event_type='join')` as the start of a registrant's interval and `coalesce(max(leave), max(join/heartbeat))` as its end — a **single** interval per registrant per session. If a registrant closes the tab and reopens it later in the same session (a refresh, a laptop sleep/resume, a flaky connection), this collapses into one continuous interval spanning the gap, during which they are counted as "concurrently present" even though they were disconnected. The RPC has no per-registrant "was there a leave/re-join in between" splitting logic.

**Mitigating factor:** the feature is currently hidden from the dashboard (`SHOW_CONCURRENT_VIEWERS = false`, `/home/user/WeWebinar/src/app/dashboard/webinars/[id]/analytics/page.tsx:40`, with a comment saying the metric "didn't land well visually, revisit later"), so this is not currently misleading any host, but the RPC and its wiring remain live and would need this fix before re-enabling.

**Remediation:** if re-enabled, build multiple `(join, leave)` sub-intervals per registrant per session from the ordered event stream (not just min/max), the same way you'd expect a real "who was online when" reconstruction to work.

## 3. HYPOTHESES / NEEDS LIVE TESTING

These could not be fully confirmed from static code alone and need a live Supabase environment (or a local `supabase start`) to verify:

1. **F-04's real-world magnitude.** Whether Vimeo/YouTube's actual reported buffering behavior, combined with `DRIFT_TOLERANCE_SECONDS=6` / `CORRECTION_COOLDOWN_MS=12000`, produces a *materially* inflated watch-time in practice (vs. the theoretical worst case reasoned about statically) needs a real slow/throttled-network test against the live room.
2. **`enforce_attendee_limit` trigger race under concurrent registration bursts** (`/home/user/WeWebinar/supabase/migrations/20260822000003_functions_and_triggers.sql:246-279`, uses `select ... for update` on the webinar row) — should serialize correctly under Postgres row locking, but wasn't load-tested here for a genuine high-concurrency registration spike (e.g. a viral webinar link).
3. **Whether a real ad-blocker/privacy extension (uBlock Origin default lists, Brave shields, Safari ITP) blocks `supabase.rpc(...)` fetch calls to a project's own `*.supabase.co` domain from the live room.** Static review shows the request goes to the tenant's own Supabase project URL, not a known third-party tracker domain, so it is *unlikely* to be blocked by domain-based filter lists — but this needs an actual browser test with common blocklists enabled to confirm `record_viewer_event`/heartbeats survive, since if they don't, both `attendee_count` and CTA "conversion_pct" (already unstable per F-01) would additionally undercount real conversions with zero visibility to the host.
4. **Whether `videoTimestampSeconds` sent to `cta_click`/`poll_response` events is ever inconsistent with the CTA's own configured `timestamp_start_seconds`/`timestamp_end_seconds` window** in a way that could be used to detect (or that currently silently tolerates) a registrant answering a poll or clicking a CTA long after the video ended, via a stale/cached page — not checked server-side (`record_viewer_event` performs no window validation) and worth confirming against real attendee behavior logs if available.
5. **Actual row-count/query-latency impact of the missing indexes (F-08)** on a webinar with a realistic large attendee count (tens of thousands) was not measured — this needs `EXPLAIN ANALYZE` against production-scale data, not just static schema review.
6. **Poll vote race condition**: the `DISTINCT ON (registrant_id, cta_id) ORDER BY occurred_at DESC` pattern (F-06 discussion) is read-time and should be robust to write races (no lost updates possible since nothing is overwritten, only appended), but whether two near-simultaneous votes from the same registrant could ever receive **identical** `occurred_at` timestamps (making `ORDER BY occurred_at DESC` non-deterministic between them) was not verified against Postgres's actual `now()` resolution/behavior under this exact query shape — worth a live concurrency test if poll accuracy is safety-critical for the product.
